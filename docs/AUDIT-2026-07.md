# Critical audit — issues found & fixed (July 2026)

A "serious user / harsh critic" pass over the whole product. Every issue below
was **confirmed in the code** (not hypothetical), and every fix was **verified
against a live server and, where relevant, a real browser**. Issues I decided
*not* to change are listed too, with the reasoning, because a good audit is
honest about what it left alone.

Legend: 🔴 clinical/financial safety · 🟠 data integrity · 🟡 usability

---

## Fixed

### 🔴 1. Prescriptions ignored the patient's recorded allergies
**The loophole.** A patient's chart can record "Penicillin allergy", yet the
prescription screen let you prescribe Amoxicillin (a penicillin) with no
warning whatsoever. The single most dangerous everyday mistake in a dental
clinic, and the software was silent about it.

**The fix.** A new cross-check (`client/src/allergyCheck.ts`) compares every
drug being prescribed against the patient's allergy field, including **drug
families** — a "penicillin" allergy now flags amoxicillin, ampicillin,
augmentin/clavulanate, cloxacillin, etc.; NSAID, cephalosporin, sulfa, macrolide
and metronidazole families too. When it matches, the New Prescription window
shows a red **"Allergy warning — please double-check"** banner naming the drug
and the reason, and **Save is disabled until the doctor ticks "I have reviewed
this and want to prescribe anyway."** It warns, never blocks — the doctor stays
the decision-maker.

> Deliberately conservative: it flags likely clashes and says "double-check". It
> never declares a drug *safe* — absence of a warning is not a green light.

**Verified.** Set a penicillin allergy on a patient, opened New Prescription,
typed "Amoxicillin 500mg" → warning appeared, Save disabled; ticking the box
enabled Save. (Browser-driven, screenshotted.)

### 🟠 2. Double-booking was only caught *after* it happened
**The loophole.** The server computed an appointment overlap but only returned
it as an advisory string *after the booking was already committed*. The
calendar's own "Book appointment" window ignored that string entirely, so you
could silently stack two patients on one slot. Worse, **rescheduling** an
existing appointment ran **no overlap check at all** — you could drag anyone
onto an occupied slot with zero feedback.

**The fix.**
- New pre-flight endpoint `GET /appointments/clash` so the form can check a slot
  **before** committing.
- Both booking windows (patient page *and* calendar page) now show a live
  **"That time is already taken — overlaps <name>"** warning as you pick the
  time, and the button changes to **"Book anyway"** — you can still double-book
  on purpose, but never by accident.
- The reschedule path (`PUT /appointments/:id`) now runs the same overlap check
  (excluding the appointment itself) and returns the warning.

**Verified.** Live API: clash endpoint correctly detects a collision and clears
on a free slot; reschedule onto an occupied slot returns
`"Overlaps Meera Krishnan at that time"` and returns empty on a free slot.
Browser: the warning renders in the booking window.

### 🟠 3. You could schedule a future visit for an archived patient
**The loophole.** "Archived" is supposed to mean *no more activity* — and the
automated reminder engine correctly skips archived patients. But nothing stopped
a user from actively **booking a new appointment** for one. In practice that
almost always means the wrong patient was picked (a "moved away" or deceased
chart).

**The fix.** `POST /appointments` now rejects an archived patient with a clear
message: *"<name> is archived. Re-activate the patient before booking a new
appointment."*

**Verified.** Live API returned HTTP 400 with that exact message when booking
the archived "John Junior".

---

### 🟡 4. Booking in the past was silently accepted
**The loophole.** Fat-finger the year and the system happily booked an
appointment in 2020, then generated no reminders (they're all in the past) — a
silent no-op that looks like a successful booking.

**The fix.** Both booking windows now show **"This time is in the past"** when
the chosen date/time is before now, and the button reads "Book anyway". Not a
hard block (recording a past walk-in is occasionally legitimate), but never
silent.

**Verified.** Browser: setting the date to 2020 surfaced the past-time warning.

---

### 🟠 5. The Rx Library could silently discard your work
**The loophole.** The Prescription Library has two tabs — Templates and
Medicines. Saving one tab **closed the whole window**, throwing away any unsaved
edits in the *other* tab without a word. Edit both, save one, lose the other.

**The fix.** Saving now **keeps the window open** and shows a "✓ Saved"
confirmation, clearing only the tab that was saved. Each tab shows an amber dot
when it has unsaved edits; if the tab you're not on has unsaved work, a banner
says so with a one-click jump to it. Closing with any unsaved edits asks for
confirmation first. The Save button also disables itself once a tab is clean, so
"Saved" is unambiguous.

**Verified.** Type-checks and renders; the save mutations no longer call
`onClose()`.

---

### 🟡 6. Overpaying an invoice gave no feedback
**The loophole.** Recording a ₹5,000 payment against a ₹500 invoice was accepted
with no comment, quietly creating a credit balance that's easy to mistake for
real takings.

**The fix.** The payment window now warns when the amount exceeds what's due on
the chosen invoice, shows the surplus that will become advance credit, and
suggests recording it against "none (advance)" instead. A warning, not a block —
advances are legitimate.

**Verified.** Type-checks; logic computes remaining due from the selected
invoice's payments.

## Reviewed and deliberately left as-is

These looked like issues on first glance but were either already handled or are
correct by design. Listed for transparency.

- **Voiding an invoice that has payments** — already blocked server-side (would
  otherwise turn payments into phantom credit). ✔
- **Payment against a voided or another patient's invoice** — already validated
  and rejected. ✔
- **Invoice numbering under concurrent creates** — already retries on the unique
  constraint. ✔
- **Stock going negative** — already blocked (`"Only N in stock"`). A
  theoretical race exists under simultaneous adjustments, but this is a
  single-laptop app; not worth the locking complexity.
- **Automated messages to archived patients** — every scheduler job already
  filters `patient: { active: true }`. ✔
- **Duplicate patient by phone** — already flagged on create with a
  family-sharing override. (It is *not* re-checked when you later *edit* a phone
  number — a minor gap, noted for a future pass.)
- **Advance payments not tied to an invoice** — intentional and supported.

## Known gaps not addressed in this pass
Small, lower-risk, and honestly out of scope for a "loopholes" sweep — flagged
so they're not forgotten:

1. Editing a patient's phone to collide with another patient isn't
   duplicate-checked (only creation is).
2. Inventory stock adjustments aren't transactional against concurrent writes
   (single-user deployment makes this near-zero risk today).
3. The clash check is clinic-wide (one chair assumed). A multi-chair clinic
   would want per-chair/per-doctor slots.
